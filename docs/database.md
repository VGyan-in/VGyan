# Database and migrations

PostgreSQL 14+ (CI and local development use 16). The schema is managed only by Alembic migrations in
`backend/alembic/versions`. The app never creates tables automatically.

| Revision | Change |
|---|---|
| 0001 | Initial schema |
| 0002 | Seeded passages and writing prompts (IDs match the app's bundled content) |
| 0003 | `reading_attempts.asr_status` (`completed`/`pending`), nullable metrics while pending, check constraints |
| 0004 | `storage_deletions` queue; index on `record_revisions(student_id)` |

## Commands

```bash
cd backend
alembic upgrade head          # apply (the Docker entrypoint does this on start)
alembic current               # show the applied revision (also in GET /health/ready)
alembic check                 # fails if models.py and migrations disagree (run in CI)
alembic revision --autogenerate -m "describe change"   # then review the file by hand
alembic downgrade -1          # only for development; 0003's downgrade refuses if pending readings exist
```

Rules:
- Migrations are forward-only in production. Review every autogenerated file.
- A migration that could lose data must refuse to run when such data exists (see 0003).
- Changing a column the app syncs needs a matching change in `app/schemas.py`, the app's `types/models.ts` and the tests.

## Integrity rules enforced by the database

- Primary keys for attempts, consent and sessions are client UUIDs (idempotent sync).
- `uq_revision_entity_rev`: one row per entity revision.
- Check constraints: languages, levels, input methods, consent status and signer, accuracy 0–100, `asr_status`, and "completed readings have metrics".
- Foreign keys from research tables to `students` are `ON DELETE RESTRICT`: a student row is never deleted, so evidence and audit links survive. Deletion empties the data and anonymises the row instead.
- `storage_deletions.object_key` is unique, so queuing the same object twice is harmless.

## Integrity checks

```bash
python -m app.cli integrity-check
```

Reports, as JSON, with exit code 1 on any problem:
- `missingObjects`: database rows that point at media missing from storage
- `orphanedObjects`: stored media no row refers to (and not queued for deletion)
- `pendingStorageDeletions`: deletions not yet confirmed
- `deletedButPresent`: objects a completed deletion should have removed but that still exist
- `deletedParticipantLeftovers`: rows still attached to a deleted participant
- `attemptsWithoutConsentRecord`: attempts from a student with no consent record at all

The test suite (`tests/test_hardening.py`) and CI (after the E2E journey in the Docker image) run it.

## Backups and restore

Use the host's managed backups (daily, with point-in-time recovery). Bucket objects are not in the
database backup: enable bucket versioning or replication separately, with a lifecycle rule that expires
non-current versions (otherwise deleted recordings survive as old versions).

Restore drill (do this before the pilot):
1. Restore the database to a new instance and point a staging API at it, with the same bucket read-only or a copy.
2. `alembic current` must show the expected revision; `GET /health/ready` must be `ok`.
3. Run `python -m app.cli integrity-check`. Expect `missingObjects` to be 0.
4. Re-apply deletions completed after the backup was taken (compare `deletion_requests.processed_at` with the backup time) and run `purge-storage`.
5. Record the time taken; that is your recovery-time estimate.
